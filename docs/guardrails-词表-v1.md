# 必说 / 禁语词表 v1.1（通用版）

> 维护：C（工程集成与 RSI）。载体：`server/agent/guardrails.yaml`。
> 生效代码：`server/agent/guardrails.py` 的 `check(state, reply, had_tool)`。
> 版本：`generic-v1.1`。官方《话术规范与合规红线》资料包到手后，整份替换为 `official-v1`。

## 1. 这份表是干什么的

指南第 8.7 节的原话是"合规护栏不只靠 Prompt，规则层兜底"。意思是：模型可能被客户一句话绕过去，光靠提示词约束不可靠，所以必须在**输出下发之前**再过一道硬规则。

这道规则只回答一个问题：**这句话能不能说出口。** 不能，就整句换成兜底话术，绝不把原文发出去。

规则分三类：

| 类别 | 判断方式 | 命中后果 |
|---|---|---|
| 禁语 | 回复中包含任一词条 | 整句替换为兜底话术 |
| 必说 | 该状态下回复**没有**包含规定内容 | 整句替换为兜底话术 |
| 隐私 | 回复中出现手机号 / 身份证号 / 银行卡号格式 | 整句替换为兜底话术 |

## 2. 禁语词表（7 类，31 条）

### 2.1 绝对化承诺（6 条）

任何"保证""绝对""百分之百"的表述都不可接受——平台无权替第三方作绝对承诺。

| 词条 | 为什么要禁 | 典型错误说法 |
|---|---|---|
| 绝对保证 | 承诺无法兑现即构成虚假宣传 | "这个方案绝对保证有效" |
| 绝对安全 | 安全是相对概念 | "您的信息绝对安全" |
| 绝对没问题 | 同上 | "到期续费绝对没问题" |
| 百分之百 | 同上 | "百分之百能续上" |
| 100% | 同上 | "100% 到账" |
| 一定能办成 | 结果不由客服决定 | "今天一定能帮您办成" |

### 2.2 虚假保证（6 条）

| 词条 | 为什么要禁 |
|---|---|
| 我保证 | 个人担保无效，且会把公司拖进责任 |
| 包您满意 | 结果不可控 |
| 无条件退款 | 退款有条款约束，不能口头扩大 |
| 内部渠道 | 暗示走后门，属不当承诺 |
| 唯一官方渠道 | 排他性表述，易构成不正当竞争 |
| 官方内部人员 | 冒充身份 |

### 2.3 诱导施压（6 条）

制造虚假紧迫感，属于骚扰式营销。

| 词条 | 为什么要禁 |
|---|---|
| 最后一次机会 | 虚假稀缺 |
| 不买就亏了 | 利益恐吓 |
| 错过就没了 | 虚假稀缺 |
| 限时秒杀 | 与业务不符的促销话术 |
| 必须今天办 | 强迫性表述 |
| 不办就停用 | 威胁性表述（真实停用需按条款单独告知） |

### 2.4 金融收益承诺（3 条）

本业务不涉及理财，出现即越界：`稳赚不赔`、`保本保收益`、`肯定赚钱`。

### 2.5 医疗效果承诺（2 条）

本业务不涉及医疗，出现即越界：`包治`、`药到病除`。

### 2.6 辱骂与歧视（5 条）

人格侮辱与地域、年龄、性别、疾病歧视，任何一条都属严重违规：
`你懂什么`、`闭嘴`、`滚出去`、`老年人就是`、`外地人就是`。

### 2.7 索要敏感信息（3 条）

客服永不主动索取：`验证码发我`、`银行卡密码`、`把身份证号发`。

> 说明：涉政、涉黄、涉暴类红线词不在通用版自行列举。这类词表以官方资料包为准，到手后按 `official-v1` 整份替换，避免自拟词条与官方口径不一致。

## 3. 必说话术（8 个状态）

必说话术按对话状态检查。状态名取自 `server/agent/fsm.py` 的 `STATES`，两边必须一致。

| 状态 | 必须包含 | 正则 | 缺了会怎样 |
|---|---|---|---|
| GREETING | 客服身份（京东/小智） | `(京东)?客服.*(身份\|小智)` | 客户不知道谁在打电话，涉嫌冒充 |
| IDENTITY_CONFIRM | 确认对方是本人 | `(本人\|您本人\|是您)` | 未确认身份就谈业务，属违规触达 |
| REQUIREMENT | 提到会员/到期/意向 | `(会员\|到期\|意向)` | 没问清需求就推方案 |
| SOLUTION | 9折 + 12个月 / 到期提醒 | `9折.*12个月\|到期(前)?提醒` | 关键条款漏说，事后易起纠纷 |
| CONFIRM | 登记 / 可以吗 | `(登记\|可以吗)` | 未征得同意就办理 |
| WRITEBACK | 已登记 / 已记录 | `(登记\|已记录)` | 客户不知道到底办没办 |
| COMPLETED | 再见 / 感谢 | `再见\|感谢` | 突兀挂断，体验差 |
| HUMAN_TRANSFER | 转接 / 人工 | `(转接\|人工)` | 说转人工却没提怎么转 |

## 4. 隐私拦截

一条合成正则，覆盖三种格式：

```
1[3-9]\d{9}        # 手机号（11 位）
\d{17}[\dXx]       # 身份证号（18 位，末位可为 X）
\d{16,19}          # 银行卡号（16–19 位连续数字）
```

出现在**回复文本**里即判泄露。注意：客户自己报出的号码落在**用户轮次**里不算泄露（那是客户说的，必须留存），拦截只针对 Agent 要说出口的内容。

## 5. 命中之后怎么处理

不管命中哪一类，处理方式统一：

1. 整句丢弃，替换为兜底话术
2. 兜底话术固定为："不好意思，这个问题我帮您转接人工客服，请稍等。"
3. 记录命中原因（`problems` 列表），供质检统计

**绝不"改一改再发"**。因为改写本身又是一次生成，可能引入新问题。整句换掉是最稳的。

## 6. 转人工触发条件

| 条件 | 阈值 | 说明 |
|---|---|---|
| 连续没听清/没推进 | 3 次 | 说明链路或客户状态有问题，别再硬撑 |
| 客户明确拒绝 | 2 次 | 第二次拒绝必须停止推销 |
| 工具不可用 | 1 次 | 查不到数据就不能编，直接转 |

这三个阈值同时在 `guardrails.yaml` 的 `transfer_to_human` 里，B 的 Agent 据此判断。

## 7. 代码怎么读这份表

`guardrails.py` 启动时读 yaml，读不到就退回代码里的内置默认值——这是为了"yaml 写坏了也不至于把护栏关掉"。

```python
from server.agent.guardrails import check
r = check("SOLUTION", "现在续费可以享9折，有效期12个月")
# r = {"ok": True, "problems": [], "reply": "原句"}
```

返回三样：`ok` 能不能发、`problems` 命中了什么、`reply` 实际该发什么。

## 8. 官方资料包到手后的替换流程

1. 把官方词表整理成同样三段结构（禁语 / 必说 / 隐私）
2. 改 `guardrails.yaml` 的 `version` 为 `official-v1`
3. **只改数据，不动 `guardrails.py`**——这是当初把词表抽成 yaml 的唯一目的
4. 跑 `bash scripts/verify_day5.sh`，8 项全过才算替换成功
5. 在 `docs/` 留一条替换记录（日期、来源、条数变化）

## 9. 质检双保险

规则层是"事前拦"，还有一道"事后扫"：

- 每通电话结束后，用 LLM-as-Judge 对**全量转写**再扫一遍
- 结果写入 `quality_issues` 表（字段：`session_id`、`rule`、`snippet`、`action`、`ts`）
- 规则层漏掉的（比如换了说法绕过去的），由这一道补上

两道都过，才算这通电话合规。这也是 Day10"质检模块 + 禁语注入测试"的前置条件。

## 10. 当前限制（必须知道）

- **31 条禁语是通用版，不是官方版**。官方资料包到手必须整份替换，否则答辩时口径对不上。
- **必说正则偏严**。比如 SOLUTION 要求同时出现 9折 与 12个月，说漏一个就整句换兜底。这会让对话显得生硬，需要在 Day6 多轮纠错时再调。
- **隐私正则的 `\d{16,19}` 偏宽**。如果将来回复里出现长订单号（16 位以上纯数字），会被误判为银行卡号。目前订单号形如 `O-7788`，暂不冲突；真出现冲突就把这条拆成带分隔符的格式。
